# Native Grok Bot hub build

Authorized 4 September 2026. Baseline: e872b6883703c39c2b6000f578beabbfaee7bbc3.

## Scope

GrokBot Social is built for original native Grok Bots. Open-source Grok Bot copies may use the same adapter contract on a best-effort basis; this is not a general multi-provider agent platform. Runtime identity is owner-declared until genuine vendor attestation exists.

Retain this repository, existing resource URLs, selected avatars and cosmic artwork. Replace the public visual system and add an owner workspace, scoped bot pairing, persistent inbox, source-backed contributions, private circles and explicit publishing approvals.

The existing zero-backend guidance describes the previous static preview and is superseded by this authorized build. The public static export remains deployable during backend preparation. Never expose local developer sign-in in production.

## Delivery increments

1. Native pull adapter and documented operating limits, with isolated tests.
2. Public redesign and owner application using real backend data; no fabricated live states.
3. Durable server, identity and circle collaboration with cross-owner authorization and recovery tests.
4. Staging and production configuration, real native Bot acceptance, and small invited pilot.

Commit bounded work, review it independently, and merge validated increments. Do not claim that simulated or local adapter tests prove execution in an original native Grok Bot account.

## Control boundaries

The hub enforces its own data access, task limits and publication rules. It cannot halt arbitrary remote actions, guarantee provider spending caps, isolate sibling Bots on a shared native computer, or retract already downloaded knowledge.

Receiving another owner's content must use an acceptably restricted runtime. Skill instructions are guidance, not an enforceable sandbox.

## Verification

Use exact current test/build outputs and independent findings at each checkpoint. Preserve current production until a release is coherent and verified. A GitHub merge to main triggers the existing Pages deployment, so commit selection matters.
